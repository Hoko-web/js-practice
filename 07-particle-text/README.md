# パーティクルテキスト（canvas）

ドットで描いた文字が、スクロールに連動して飛び散る表現を作る。
1日1ステップ × 4日の連載形式で、1フォルダに積み上げていく。

- ① canvas基礎 ＋ ランダムなドットをばらまく
- ② ドットで文字「canvas」を描く（`fillText` + `getImageData`）
- ③ アニメーションの基礎（`requestAnimationFrame`）← イマココ
- ④ スクロール連動で飛び散る（スクロール進捗 + 線形補間）

---

## ① canvas基礎 ＋ ランダムドット

### 何を作ったか

canvas 全面に、白い小さなドット（4px角）を300個ランダムにばらまいた静止画。
パーティクル表現の土台となる「canvasに点を打つ」を最小構成で実装。

### なぜ・どこで使うか

普通のLP・コーポレートサイトは画像とCSSで足りるので canvas の出番は少ない。
ただしパーティクル背景・動く背景・署名パッド・画像加工・グラフ（Chart.js の中身）など、
「CSSでは無理なリッチ表現」で武器になる。差別化要素として持っておくと強い。

### 実装のポイント

- **canvasは「サイズが2つ」ある**のが最大の関門。
  - 中身の解像度（`canvas.width` / `canvas.height`、初期値300×150）
  - 見た目の表示サイズ（CSSの `width` / `height`）
  - この2つがズレると、小さい絵を引き伸ばして表示することになり**ボケる**。だからJSで合わせる（＝サイズ同期）。
- サイズ同期は `canvas.clientWidth / clientHeight` を使った。
  - `window.innerWidth` でなくこちらにした理由：**表示サイズを決めるのはCSSの仕事**、JSは**その結果を読んで合わせるだけ**、と役割を分けられるから。CSSの値を変えてもJS側が自動で追従する。
- `const ctx = canvas.getContext("2d")` … canvasに描くとき必ず最初に呼ぶ（2D用。3D=webglもある）。`fillRect` も `fillStyle` もすべて `ctx.` で呼ぶので、1回受け取って変数 `ctx` に入れて使い回す。
- `ctx.fillStyle`（色）は**ループの外で1回だけ**、座標 `x` / `y` は**ループの中で毎回**計算する。
  - 外に出すと `Math.random()` が1回しか走らず、同じ座標に300回重ね塗り → 1個に見えてしまう。「毎回変えたい値はループの中」。
- ランダムな位置は `Math.random() * canvas.width`。`Math.random()` は0以上1未満なので、幅・高さを掛けて画面全体に散らす。

### つまづき＆気づき

- 最初「何も描けない」状態になった。原因はCSSの `width: 100vh`（`vw` のタイポ）と、白ドットが小さくて見えていなかったこと。`console.log` でサイズを確認 → でかい四角でテスト描画、の順で切り分けた。
- `ctx` が何者か最初ピンとこなかったが、「**`fillRect` などの描画命令はぜんぶ `ctx` のもの。`getContext` でそれを受け取って使い回す**」と捉えたら腹落ちした。

## ② ドットで文字「canvas」を描く

### 何を作ったか

ランダムだったドットを、「canvas」という文字の形に並べた静止画。
手で座標を計算するのは不可能なので、**一度ふつうに文字を描いて、そのピクセルを読み取り、文字があった場所にだけドットを打ち直す**という方法で実現した。

### なぜ・どこで使うか

`getImageData`（ピクセル読み取り）自体は、カラーピッカー・画像加工・モザイク処理などで使う技術。
今回はその応用で、ヒーローセクションの“魅せ”系演出（文字がパーティクルになる類）の土台。次のステップでこれを動かす。

### 実装のポイント

- 全体の流れは **描く → 読む → 覚える → 消して打ち直す** の4段階。
  1. `ctx.fillText("canvas", 中心x, 中心y)` で文字を1回描く（`textAlign:center` / `textBaseline:middle` で `(x,y)` が文字の中心になる）。
  2. `ctx.getImageData(0,0,幅,高さ)` で全ピクセルの色データを取得。
  3. 文字があったピクセルの座標を配列 `dots` に貯める。
  4. `ctx.clearRect(...)` でベタ塗りの文字を消し、`dots` の座標にドットを打ち直す。
- **ピクセルデータの構造**：`imageData.data` は「1ピクセル＝R, G, B, A（透明度）の4つ」が一直線に並んだ長い数字の列。pixel(x, y) のデータが始まる位置は `(y * width + x) * 4`、その4つ目（`+3`）が透明度。
- **透明度で文字を判定**：文字を描いた所は透明度が高い（255に近い）、何もない所は0。`alpha > 128`（0〜255の真ん中で線引き）で「文字があるか」を判定した。閾値を上げると細く、下げると太くなる調整つまみ。
- **間引き（`gap`）**：全ピクセルを拾うとドットが詰まってベタ塗りになるので、6個おきにチェックして粒感を出した。
- 集めた `dots`（文字の形の座標リスト）は、③④の「飛び散るアニメ」でそのまま材料になる。だから描くだけでなく配列に貯めている。

### つまづき＆気づき

- `(y * width + x) * 4` の意味が最初まったく掴めなかった。「データは1本の長い列。文章みたいに左→右・上→下に読む」「1ピクセル＝4つの数字」と分けて考えたら、`行を飛ばす→列を進む→4倍→+3で透明度` という流れがやっと腹落ちした。
- `for...of` は「配列の中身を1個ずつ取り出す」ループ。回数を数える `for (let i...)` と違い、番号が要らないときはこっちが読みやすい。

## ③ ドットを文字の形に集めるアニメ

### 何を作ったか

バラバラの位置に散らばったドットが、スーッと動いて「canvas」の文字に集まってくるアニメーション。`requestAnimationFrame` で毎フレーム描き直すことで「動き」を作った。

### なぜ・どこで使うか

`requestAnimationFrame` は、canvasアニメ・スクロール演出・なめらかなUI動作など「JSで毎フレーム何かを動かす」場面の土台。`setInterval` より滑らかで省エネなので、アニメ系はこれが定番。今回のヒーロー演出にも、汎用のアニメ知識としても効く。

### 実装のポイント

- **アニメの正体は「パラパラ漫画」**。`animate()` 関数の中で **消す → 位置を少し動かす → 描く** を行い、最後に `requestAnimationFrame(animate)` で自分自身を予約。これが秒60回ほど繰り返されて動いて見える。最初の1回は手で `animate()` を呼んで起動する。
- **ドットに「今の位置」と「ゴール位置」の2つを持たせた**。
  - `x` / `y` … 今の位置（最初はランダムに散らばらせる）
  - `baseX` / `baseY` … ゴール（②で集めた文字の座標）
  - 2つ要る理由：移動量は「ゴールとの差」から計算するので、今いる場所と行き先の両方が必要。
- **イージング（だんだん減速）**：`dot.x += (dot.baseX - dot.x) * 0.05` で「ゴールとの差の5%だけ毎フレーム進む」。差が大きいほど速く、近づくほど遅くなり、ゴール手前で自然に止まる。係数を小さくするほどゆっくり集まる。
- **毎フレーム `clearRect` で前のコマを消す**のが重要。消さないと前の位置のドットが残って、軌跡だらけになる。

### つまづき＆気づき

- 「今の位置」と「ゴール位置」をなぜ別々に持つのか最初ピンとこなかったが、「移動は “差 × 割合” で計算する → だから現在地と目的地の両方が要る」と分かって納得した。
- `clearRect` で消すのは画面の見た目だけで、位置の数字（変数）は消えない。だから毎フレーム消しても、ドットは続きから動ける。
- 係数を `0.1` → `0.05` に変えると集まる速さが変わる。数字ひとつで動きの印象が変わるのが面白かった。
